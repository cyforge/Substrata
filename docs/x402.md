# x402 protocol

Substrata implements the HTTP transport for x402 version 2. The wire models use
Python field names and emit the protocol's camelCase JSON representation.

## HTTP exchange

1. The client sends the original request without payment.
2. The provider returns HTTP 402 with `PAYMENT-REQUIRED`.
3. The client checks policy, reserves spend, and signs a supported offer.
4. It retries the same request once with `PAYMENT-SIGNATURE`.
5. The provider verifies and settles through its facilitator before invoking the
   protected handler. It returns `PAYMENT-RESPONSE` with the result.

Headers contain base64-encoded JSON. The SDK rejects duplicate JSON keys,
malformed base64, invalid field types, non-finite numbers, and oversized input.

## Build a local challenge

```python
from substrata.x402 import (
    PaymentRequired,
    PaymentRequirements,
    ResourceInfo,
    decode_payment_required_header,
    encode_payment_required_header,
)

offer = PaymentRequirements(
    scheme="substrata-demo",
    network="stellar:testnet",
    amount="1000000",
    asset="XLM",
    pay_to="demo-merchant",
    max_timeout_seconds=60,
)
challenge = PaymentRequired(
    resource=ResourceInfo("http://127.0.0.1:8091/paid"),
    accepts=(offer,),
)
header = encode_payment_required_header(challenge)
assert decode_payment_required_header(header) == challenge
```

The `amount` field is an atomic-unit integer string. At seven decimals,
`"1000000"` represents 0.1 tokens. It is not a human-readable decimal price.

## Connect a facilitator

```python
import os
from substrata.x402 import HTTPFacilitator

facilitator = HTTPFacilitator(
    os.environ["SUBSTRATA_FACILITATOR_URL"],
    api_key=os.environ.get("SUBSTRATA_FACILITATOR_API_KEY"),
    timeout=30,
)
supported = facilitator.supported()
assert supported.supports("exact", "stellar:testnet")
```

The adapter calls `/supported`, `/verify`, and `/settle`. URLs require HTTPS,
with loopback HTTP allowed for development. It bounds responses, disables
redirects, and does not automatically retry settlement. A failed or timed-out
settlement call may follow a successful network submission.

## Stellar exact payments

Use `scheme="exact"` with `stellar:testnet` or `stellar:pubnet`. The asset is a
Soroban contract address. Requirements must include `extra={"areFeesSponsored": True}`.
The signed payload contains `transaction`, a base64 XDR transaction with signed
authorization entries. The facilitator rebuilds and submits the transaction,
paying its fees.

`StellarAuthSigner` checks that the token reports seven decimals and that its
transfer matches the offer before signing. See [the Stellar guide](stellar.md).

## Receipt boundaries

A receipt reports the provider's settlement claim. The buyer checks the offer's
network, transaction identifier, amount when present, and expected payer. It does
not independently query Stellar. The [verified testnet run](testnet-settlement.md)
adds independent RPC and balance checks to that application flow.

The generic `SettlementResponse` model also represents off-chain schemes, which
can have an empty transaction identifier. Substrata's Stellar exact and local
demo callers apply their stricter receipt checks in context.

## Local demo scheme

`create_local_demo_pair()` returns a signer and facilitator with a shared HMAC
key. This separate `substrata-demo` scheme accepts loopback resources on
`stellar:testnet` and produces `demo:` receipts. It never submits a transaction.

For authoritative wire semantics, consult the
[x402 v2 specification](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md)
and [Stellar exact scheme](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_stellar.md).
